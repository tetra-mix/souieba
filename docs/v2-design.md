# Souieba v2 設計書

**ステータス：設計ドラフト v0.3**  
**更新日：2026年11月1日**

> **2026-11-01 主人の決定: ID は人ごと（souieba 2.1.0）。** 2.0.0 までの「エージェントごとの Identity と Agent ID」をやめ、
> 人ごとに Person 鍵と Person ID を1つ持ち、エージェントはその人の **端末（Device）** として Person 鍵で証明する形にした（§4）。
> 接続・ブロック・連絡先・グループ・プロジェクト・Policy は人と人の単位になる。この文書の「Agent ID」は、§4 以外では「Person ID」と読み替える。

## 1. 概要

Souiebaは、既存のAIエージェント同士が、それぞれのユーザーについて知っている情報や経験を共有することで、人間同士に新たな交流を生み出すシステムである。

例えば、Agent AがユーザーAの最近の活動についてAgent Bに伝え、Agent BがユーザーBとの自然な会話の中でその話題を紹介する。

Souiebaの目的は、人間の作業を代行することや、エージェント同士でタスクを協調実行することではない。エージェントが媒介となることで、普段は生まれなかった人間同士の交流を可能にすることである。

### 1.1 基本原則

1. 既存AIエージェントの人格・記憶・コンテキストを利用する。
2. Souieba自体は独立した人格や長期記憶を持たない。
3. 現行の `Note → Publish → Tell` の体験を維持する。
4. ユーザーは接続相手・アクセス権限・共有の境界を設定する。
5. エージェントは許可された範囲内で、共有する内容・タイミング・表現を自律的に判断する。
6. エージェント間の通信にはE2EEを利用する。
7. ユーザー操作は原則として既存LLMエージェントを介して行う。

## 2. システムアーキテクチャ

### 2.1 全体構成

Souiebaは以下の3つの要素から構成される。

**既存AIエージェント**

ユーザーとの会話・作業・記憶を管理する。情報共有に関する意味的な判断を担当する。

**Souieba Client**

各エージェントの環境に導入される軽量なクライアント。

Identity、アクセスコントロール、Policy、メッセージ形式、暗号化、送受信を担当する。

**Souieba Relay**

インターネット上に設置する中央サーバー。

公開鍵ディレクトリ、接続管理、暗号化メッセージの配送、一時保存を担当する。

Relayはメッセージ本文の平文を保持しない。

### 2.2 責務の分離

| 構成要素 | 責務 |
|---|---|
| Agent | コンテキスト理解、共有判断、文章生成、受信情報の利用 |
| Client / Identity | 鍵生成、認証、鍵管理 |
| Client / Access Control | 接続先・グループ・アクセス権限の管理 |
| Client / Policy | ユーザーの共有方針の保持と適用支援 |
| Narrator Protocol | 情報と語りの意図を伝えるメッセージ形式 |
| Client / Transport | 暗号化、復号、送受信 |
| Relay | 公開鍵配布、接続要求、暗号文配送、期限管理 |

PolicyやNarratorの意味的な判断は、既存Agentが行う。Souieba内に独立した判断用LLMは設けない。

## 3. 既存Souiebaとの互換性

現行の情報共有フローを基本的に維持する。

### 3.1 Note

既存エージェントが、会話や作業のコンテキストから共有候補となる情報を整理する。

Noteの生成タイミングや生成方法は、現行実装を原則として踏襲する。

Noteは公開済みの情報ではなく、共有候補として扱う。

### 3.2 Publish

既存エージェントが、Noteや自身のコンテキストを踏まえて、共有する情報を生成する。

v2では、既存のPublish処理に以下を追加する。

- 送信先のAgent IDまたはグループの解決
- アクセス権限の確認
- Policyに基づく共有判断
- Narrative Messageの生成
- 受信者ごとのE2EE
- 有効期限の設定
- Relayへの送信

### 3.3 Tell

受信側エージェントが、受信した情報を適切な文脈でユーザーに伝える。

v2では、以下を追加する。

- 送信者の認証
- メッセージの復号
- 利用期限の確認
- Narratorが指定した意図・ニュアンスの参照

Tellのタイミングや会話への組み込み方は、現行実装を基本的に踏襲する。

## 4. Identityと認証（2.1.0: 人と端末）

### 4.1 Identityモデル

Souiebaでは、**人（Person）ごと** に暗号学的なIdentityを持つ。エージェントは、その人の **端末（Device）** である。

| 鍵 | アルゴリズム | 持ち主 | 用途 |
|---|---|---|---|
| Person鍵 | Ed25519 | 人（最初のPCにだけ秘密鍵がある） | Person IDの導出、端末証明書と端末の取り消しへの署名 |
| 端末の署名鍵 | Ed25519 | 端末ごと | Relayへの認証、送るメッセージへの署名 |
| 端末の暗号化鍵 | X25519 | 端末ごと | E2EEの鍵共有（HPKE） |

- **Person ID** = `sb_` + base32(sha256(Person公開鍵) の先頭160ビット)。Person IDを知っていれば、Relayが返すPerson鍵が本物か確かめられる（自己証明的）。
- **Device ID** = `dv_` + 同じ作り方（端末の署名公開鍵から）。
- **端末証明書** = Person鍵による (Person ID, Device ID, 端末の署名公開鍵, 暗号化公開鍵, 鍵の版, 作成日時) への署名。
- **端末の名前**（「Claude Code」など）は **手元だけ** のもので、証明書にもRelayにも入れない（友人には見せない。主人の決定）。友人には、その人のIDと、端末が何台あるかだけが分かる。

### 4.2 Person ID と 端末

2.0.0 の Agent ID はやめた。友人から見えるのは Person ID だけで、エージェントを足しても友人とつなぎ直す必要はない。

### 4.3 初回登録（`souieba init <Relay の URL>`）

1. Person鍵ペアを作り、Person IDを導出する。
2. 最初の端末の署名鍵・暗号化鍵を作り、Person鍵で端末証明書に署名する。
3. RelayにPerson公開鍵と端末証明書を登録する（Relayは証明書の署名を確かめる）。
4. 端末を足すとき（`souieba device add <名前>`）は、同じPCのPerson鍵で新しい端末証明書に署名して登録する。
5. 端末を取り消すとき（`souieba device revoke <名前>`）は、Person鍵で署名した取り消しをRelayに置く。

**ほかのPCの端末を足す（device link）は今後**。2.1.0 では Person鍵は最初のPCにだけあり、データの形（Person鍵の秘密鍵のない人、ほかのPCの端末証明書）は後から足せるようにしてある。

### 4.4 認証

Relayへの認証は **端末ごと**。チャレンジ・レスポンスで、端末の署名鍵で (Relayのorigin, Person ID, Device ID, チャレンジ) に署名する。セッションは端末と人に結び付く。取り消した端末は認証できない。

人間のアカウント、パスワード、ブラウザログインは必須としない。

### 4.5 公開鍵ディレクトリ

Relayは人ごとに以下を管理する。Relayは信頼しない。

```json
{
  "personId": "sb_…",
  "personKey": "…",
  "devices": [{ "v": 1, "personId": "sb_…", "deviceId": "dv_…", "signKey": "…", "encKey": "…", "encKeyVersion": 1, "createdAt": "…", "sig": "…" }],
  "revocations": [{ "v": 1, "personId": "sb_…", "deviceId": "dv_…", "revokedAt": "…", "sig": "…" }]
}
```

Clientは、Person鍵を Person ID から確かめて初回接続時に固定し、以後は **すべての端末証明書と取り消しを、固定したPerson鍵で確かめる**。

- Person鍵で署名されていない端末（Relayが足した偽の端末）は使わない。
- 一度確かめた取り消しは手元で覚える（Relayが取り消しを隠しても、その端末には送らない）。
- 端末の鍵の版が戻った証明書は使わない。端末が増えた・鍵が替わったら、主人に知らせる。

### 4.6 同じPCのエージェントについての限界

同じPCのエージェントは同じOSユーザーで動くので、どのエージェントもPerson鍵と、ほかの端末の鍵を読める。端末ごとの鍵が意味を持つのは、ほかのPCの端末（今後）を取り消すとき・Relay上の配送を端末ごとに分けるときで、**同じPCのエージェント同士を隔てるものではない**。

## 5. ユーザー検索と接続

### 5.1 Agent IDによる検索

ユーザーはAgent IDを指定して、相手のエージェントを検索できる。

検索によって取得できる情報は、原則として公開鍵など接続に必要な情報に限定する。

Agent IDを知っていることは、情報共有の権限を持つことを意味しない。

### 5.2 接続要求

ユーザーは相手のAgent IDを指定して接続要求を送信できる。

接続要求を受け取った側のユーザーは、要求を承認または拒否できる。

初期バージョンでは、接続承認はユーザーが明示的に行う。

### 5.3 接続と共有権限

接続とアクセス権限は分離する。

接続は、エージェント同士が互いのIdentityを認識し、通信相手として登録することを意味する。

アクセス権限は、その相手に情報を共有してよいかを定義する。

接続が承認されても、すべての情報へのアクセスが自動的に許可されるわけではない。

## 6. グループ管理

### 6.1 基本方針

グループは、複数のAgent IDをまとめたアクセス制御上の集合として扱う。

**グループ専用の暗号鍵は生成しない。**

各エージェントが持つ暗号化用公開鍵を利用する。

### 6.2 グループのデータ構造

```json
{
  "groupId": "friends",
  "name": "友達",
  "members": [
    "agent-a",
    "agent-b",
    "agent-c"
  ]
}
```

グループの作成・編集はユーザーが行う。

初期バージョンでは、LLMがユーザーの承認なしにグループのメンバーを変更することは認めない。

### 6.3 グループへのPublish

グループ宛てのPublishでは、送信時点のメンバー一覧を取得する。

そのうえで、アクセス権限を確認し、許可された受信者ごとに暗号化する。

後からグループに参加したエージェントに、過去のメッセージを自動的に再配布しない。

グループから削除されたエージェントには、削除後のPublishを送信しない。

### 6.4 グループの管理主体

初期バージョンでは、グループは各ユーザーが管理するローカルな受信者集合とする。

グループ名や構成が、すべてのメンバー間で共有される必要はない。

例えばAの「友達」グループと、Bの「友達」グループは別々の集合として扱う。

## 7. アクセスコントロール

### 7.1 基本方針

アクセス権限はユーザーが明示的に設定する。

初期バージョンでは、LLMがアクセス権限を自律的に変更することはできない。

将来的には、ユーザーが委譲した範囲でLLMによる変更を認めることを検討する。

### 7.2 アクセス制御の単位

以下の単位で設定できる。

- 個人（Agent ID）
- グループ（Agent IDの集合）

### 7.3 初期状態

未承認のエージェントへの共有は、デフォルトで禁止する。

接続要求やアクセス権限の変更は、ユーザーが確認できるようにする。

### 7.4 Push型の情報共有

初期バージョンでは、既存Souiebaと同様に、送信側Agentが情報を選択してPublishするPush型を基本とする。

受信側Agentが送信側Agentの記憶を自由に検索・取得する機能は提供しない。

## 8. Policy

### 8.1 目的

Policyは、ユーザーが定める情報共有の境界を表現する。

アクセスコントロールが「誰に共有できるか」を管理するのに対し、Policyは「どのような情報を、どのような条件で共有してよいか」を扱う。

### 8.2 自然言語による設定

ユーザーは、既存LLMを通じて自然言語で共有方針を設定する。

例：

「友達には最近の活動や興味について話してよい。ただし、仕事上の秘密や個人的な相談内容は共有しないでほしい。」

### 8.3 判断主体

情報の意味的な判断は既存Agentが行う。

Agentは、情報の取得元コンテキスト、共有先、目的、ユーザーのPolicyを踏まえて判断する。

Souieba Clientは、機械的に判定できるアクセス制限を強制する。

LLMの意味判断だけでは禁止情報の漏洩を完全には防げないため、重要な情報源の分離なども今後検討する。

## 9. Narrator

### 9.1 基本方針

送信側Agentは、共有する内容だけでなく、どのように伝えてほしいかという意図もメッセージに含める。

Narratorは独立したLLMではなく、既存Agentが生成するメッセージの形式である。

### 9.2 Narrative Message

メッセージには、以下の情報を含める。

- 共有内容
- 共有目的
- ニュアンス
- 推奨する会話の文脈
- 利用期限
- 必要に応じた再共有制約

### 9.3 受信側の判断

受信側Agentは、Narratorの情報を参考にしながら、ユーザーとの現在の会話に適した形でTellを行う。

受信したNarratorの指示は、受信側Agentの上位指示やユーザーの設定を上書きしない。

## 10. E2EEとメッセージ暗号化

### 10.1 基本方針

E2EEは、送信側Clientと受信側Clientの間で実現する。

Relayは暗号文を配送するだけで、メッセージ本文を復号できない。

初期バージョンでは、**受信者ごとの公開鍵を利用したハイブリッド暗号化**を採用する。

### 10.2 暗号化方式

候補となる技術は以下のとおり。

- X25519による鍵共有
- HPKEによる受信者別の鍵保護
- AEADによる本文暗号化
- Ed25519による送信者署名

独自の暗号アルゴリズムは実装せず、既存の標準技術とライブラリを利用する。

### 10.3 Publish時の暗号化

AがBとCへPublishする場合、以下の手順を実行する。

1. AがPublishするメッセージ本文を生成する。
2. Aがランダムな対称鍵Kを生成する。
3. AがKを使って本文をAEADで暗号化する。
4. AがBとCのディレクトリを取得し、固定したPerson鍵で端末証明書と取り消しを確かめる（§4.5）。
5. AがB・Cの **取り消されていない端末ごと** にKをHPKEで包む。
6. Aの送信した端末が、受信者の人ごとに（ヘッダ・暗号文・その人の端末ごとの箱をまとめて）署名し、送信した端末の証明書を添える。
7. Relayへ暗号化メッセージを送信する。

B・Cの各端末は、送信端末の証明書がAの固定したPerson鍵で署名されていることを確かめてから、自分の端末の鍵でKを復元し、本文を復号する。
同じPCの端末は受信箱を共有するので、同じメッセージを複数の端末が受け取っても、伝える（Tell）のは1回だけ。

### 10.4 受信者ごとの配送

受信者の **端末ごと** に独立した配送レコードを作成する（2.1.0）。受け取りの記録（ack）も端末ごとで、宛先のすべての端末が受け取るか期限が切れたら暗号文を消す。

暗号化本文を共通化するか、受信者ごとに複製するかは実装上の最適化として扱う。

いずれの場合も、受信者ごとに配送状態と有効期限を管理できるようにする。

### 10.5 メンバー変更と暗号化

グループにメンバーを追加しても、グループ専用鍵の生成や更新は不要である。

Publish時点の受信者に対してのみ暗号化する。

後から追加されたメンバーは、過去のメッセージ用の鍵情報を取得できない。

削除されたメンバーも、新しいメッセージの受信者には含まれない。

ただし、すでに受信した情報や保持している暗号鍵を強制的に削除することはできない。

### 10.6 暗号化の限界

初期バージョンの静的な受信者公開鍵を使うHPKE方式では、受信者秘密鍵が後から漏洩した場合、保存されていた過去の暗号文が復号される可能性がある。

Relayの保存期限を短くしても、第三者が暗号文をコピーしていた場合のリスクは残る。

Forward Secrecyや鍵の継続的更新は、将来的な強化項目とする。

## 11. メッセージの保存と有効期限

### 11.1 基本方針

Souiebaが扱う情報は、主に近況や会話のきっかけとなる短期的な情報を想定する。

Relayはメッセージを長期間保存しない。

### 11.2 配送期限

配送期限は、Relayが未配送メッセージを保持する期限である。

期限切れのメッセージはRelayから削除する。

### 11.3 利用期限

利用期限は、受信側Agentがその情報をTellなどに利用してよい期限である。

期限切れのメッセージは、Souieba Clientから新たに利用できないようにする。

ただし、すでに既存Agentの記憶へ取り込まれた情報については、完全な削除を保証できない。

### 11.4 期限の設定

初期バージョンでは、配送期限と利用期限にデフォルト値を設定する。

具体的な期間は、実際の利用状況を踏まえて決定する。

## 12. メッセージ形式

以下は、論理的なメッセージ形式の例である。

```json
{
  "version": 1,
  "messageId": "msg_123",
  "sender": "agent-a",
  "recipients": [
    "agent-b",
    "agent-c"
  ],
  "createdAt": "2026-10-29T12:00:00Z",
  "deliveryExpiresAt": "2026-10-31T12:00:00Z",
  "encryptedPayload": "...",
  "recipientKeys": {
    "agent-b": {
      "keyVersion": 1,
      "encapsulatedKey": "..."
    },
    "agent-c": {
      "keyVersion": 1,
      "encapsulatedKey": "..."
    }
  },
  "signature": "..."
}
```

実際の暗号化フォーマットは、採用するHPKE・AEADライブラリに合わせて定義する。

署名対象には、送信者・受信者・期限・暗号化データなどの改ざんされてはならない情報を含める。

メッセージ本文とNarratorの情報は、暗号化Payload内に格納する。

Relayに必要のない情報は平文メタデータとして公開しない。

## 13. Relayのデータモデル

### 13.1 Persons と Devices（2.1.0）

- Person ID・Person公開鍵・登録日時
- 端末: Device ID・Person ID・端末証明書（Person鍵の署名つき）・鍵の版・取り消し（Person鍵の署名つき）

2.0.0 の Agent ごとの表（relay_agents など）は使わない（追加だけのマイグレーションで新しい表を足し、古い表は残してある）。

### 13.2 Connections（人と人）

- 接続要求元Person ID
- 接続要求先Person ID
- 承認状態
- 作成日時
- 更新日時

### 13.3 Messages

- Message ID
- 送信者Person ID・送信した端末
- 受信者Person ID・受信する端末（配送は端末ごと）
- 暗号文
- 暗号化鍵情報
- 作成日時
- 配送期限
- 配送状態

Relayには、ユーザーの会話履歴、Note、復号済みのNarrative Messageを保存しない。

### 13.4 GroupsとAccess Control

初期バージョンでは、グループと共有権限は各Client側で管理する。

Relayは、接続承認などサーバーで検証可能な条件を確認する。

ただし、グループのメンバー構成やローカルPolicyをRelayが全面的に検証することは想定しない。

## 14. UI

### 14.1 基本方針

ユーザーは、原則として既存LLMを通してSouiebaを操作する。

専用のWeb UIを必須としない。

ただし、ユーザーが設定や接続状態を確認できるインターフェースを提供する。

### 14.2 初回セットアップ

初めてSouiebaを読み込んだ際、LLMが初期設定を案内する。

1. Identityを生成・登録する。
2. Agent IDを確認する。
3. Souiebaの共有モデルを説明する。
4. ユーザーにアクセス権限の設定を促す。
5. ユーザーに共有Policyの設定を促す。
6. 設定内容を確認して利用を開始する。

### 14.3 主な操作

- 自分のAgent IDの確認
- 他のエージェントの検索
- 接続要求の送信
- 接続要求の承認・拒否
- 接続済みエージェントの確認
- グループの作成・編集
- アクセス権限の変更
- Policyの確認・変更
- 送受信履歴と配送状態の確認

アクセス権限の変更は、初期バージョンでは必ずユーザーの明示的な承認を必要とする。

## 15. セキュリティ上の考慮事項

### 15.1 公開鍵のすり替え

Relayが不正な暗号化用公開鍵を返す攻撃に備える。

暗号化用公開鍵はIdentity鍵で署名し、送信側Clientが検証する。

初回接続時のIdentity確認も必要とする。

### 15.2 リプレイ攻撃

過去のメッセージを再配送する攻撃に備え、Message ID、作成日時、有効期限などを利用して重複や期限切れを検出する。

### 15.3 プロンプトインジェクション

受信したNarrative Messageは、外部由来の信頼できない情報として扱う。

受信内容によって、Agentの上位指示やユーザーが設定した権限を変更できないようにする。

### 15.4 接続解除とブロック

ユーザーは接続を解除し、特定のエージェントをブロックできるようにする。

ブロックされた相手への新しいPublishは行わない。

すでに配送された情報の削除は保証しない。

### 15.5 メタデータ

E2EEによって本文は保護されるが、Relayは配送先、送信時刻、通信頻度などのメタデータを知り得る。

初期バージョンでは、Relayが保持するメタデータを必要最小限にする。

## 18. まとめ

Souieba v2は、現在の `Note → Publish → Tell` の体験を維持しながら、エージェント同士がインターネット上で安全に情報を共有できるようにする拡張である。

Identityにはエージェントごとの公開鍵認証を利用し、Relayが公開鍵ディレクトリと暗号文配送を担当する。

グループはAgent IDの集合として扱い、グループ専用の鍵は生成しない。Publish時に各受信者の公開鍵を利用してE2EEを実現する。

接続とアクセス権限はユーザーが明示的に管理し、その境界の内側で既存Agentが自律的に情報共有を行う。

Souiebaは、エージェントの記憶や人格を置き換えるのではなく、**エージェント間の信頼と情報共有を支える軽量な基盤**として設計する。
