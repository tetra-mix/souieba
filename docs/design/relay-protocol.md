# Relay のプロトコルと信頼モデル

人と人を接続し、暗号化した近況を届ける仕組みを決める。ID と鍵の作り方、接続の扱い、メッセージの形式と暗号化・署名、送受信での検証、Relay が見られる情報と信頼の限界を書く。サーバの構成や運用は [server.md](server.md)、送られる中身を作る流れは [post-flow.md](post-flow.md) を見る。

## 1. 登場するもの

| もの | 内容 |
|---|---|
| Person | 人。Ed25519 の Person 鍵を1つ持つ。外から見える主体はこれだけ |
| Device | Person の端末（この PC のエージェントが使う内部の転送端末）。端末ごとに署名鍵（Ed25519）と暗号化鍵（X25519）を持つ |
| Relay | 公開鍵の置き場・接続の仲介・暗号文の配送と期限管理だけを行うサーバ |
| Client | 各 Person の PC 側。連絡先・グループ・共有先・Policy・メモ・受信箱は Client が持ち、Relay には置かない |

外部インターフェース（CLI の引数や友人から見える情報）に、エージェントの種類や端末の名前は出ない。端末の名前は手元だけのもので、証明書にも入れない。

## 2. ID と鍵

- **Person ID** は `sb_` に、Person 公開鍵（生の32バイトの base64url）の SHA-256 の先頭160ビットを base32（小文字）にした32文字を付けたもの。鍵から作るので、ID を知っていれば、その鍵を確かめられる（自己証明的）
- **Device ID** は `dv_` に、端末の署名公開鍵から同じ作り方で作った32文字を付けたもの
- **端末証明書（device cert）** は、端末の署名鍵・暗号化鍵・暗号化鍵の版（`encKeyVersion`）・作成時刻を、Person 鍵で署名したもの。その端末がその人のものだと示す
- **端末の取り消し（revocation）** も Person 鍵で署名する。一度取り消した端末は戻せない
- 1人が使える端末は取り消していないもので10台まで
- Person の秘密鍵は、`souieba init` を実行した PC の `config.json`（所有者だけが読める権限）にある。端末の鍵も同じ場所にある

署名・鍵の形式は `node:crypto` だけで実装している。署名は Ed25519、鍵は JWK の `x`・`d`（生の32バイトの base64url）で扱う。往復して同じ文字列に戻らない鍵（末尾の余りビットが違う別の書き方）は、同じ鍵として扱わず断る。

## 3. 公開鍵ディレクトリ

Relay は、人ごとに Person 鍵・端末証明書・取り消しを持つ（`PersonDirectory`）。

- **登録**（`POST /v2/devices`）: Person 公開鍵と端末証明書を送る。Relay は「Person ID が鍵から作った値と合う」「証明書の署名が Person 鍵で合う」ことだけを確かめて保存する。Person 鍵で署名された証明書を作れること自体が、鍵の所有の証明になる。初めての人なら人も作る。同じ端末の再登録はそのまま通り、鍵の版が上がった証明書なら置き換える。別の人のものとして登録済みの端末や、取り消した端末は断る
- **取り消し**（`POST /v2/devices/revoke`）: Person 鍵で署名した取り消しを送る。その端末のセッション・チャレンジ・未配送の配送を消す
- **引き当て**（`GET /v2/persons/:id`、`POST /v2/persons/lookup`）: Person ID を指定して、その人のディレクトリを返す。認証した端末なら誰でも引けるが、一覧や検索の API はない。1回に引けるのは50人まで

**ディレクトリは信頼しない。** 受け取った側は `verifyPersonDirectory` で次を確かめ、使ってよい端末だけを取り出す。

1. Person ID が鍵から作った値と一致する
2. 固定した Person 鍵（連絡先に保存したもの）があれば、それと同じである
3. 署名の合わない証明書・取り消しは捨てる（Relay が偽の端末を足しても、証明書の署名が合わず使われない）
4. 以前確かめた取り消しは覚えておき、Relay が取り消しを隠しても、その端末は使わない
5. 同じ端末の証明書が複数あれば、鍵の版が最大のものを使う

送る側は、さらに連絡先に覚えている端末の鍵の版より小さい版を返された端末を使わない（Relay が古い証明書を返す巻き戻しへの対策。`key_rollback`）。端末が増えたり暗号化鍵が替わったりしたら、連絡先を更新して、次の tell で主人に知らせる。

## 4. 認証

端末ごとに、チャレンジ・レスポンスで認証する。

1. `POST /v2/auth/challenge` に Device ID を送ると、ランダムな32バイトのチャレンジ（有効2分）を返す
2. 端末の署名鍵で、`souieba/v2/device-auth`・Relay の origin・Person ID・Device ID・チャレンジを改行でつないだ文字列に署名して `POST /v2/auth/session` に送る
3. 合っていれば、セッショントークン（`sou_r_…`、有効1時間）を返す。Relay はトークンの SHA-256 だけを保存する

チャレンジは成否にかかわらず1回で使い切る。署名する文字列に Relay の origin を含めるので、別の Relay への使い回しはできない。Client はトークンを端末の状態ディレクトリに所有者だけが読める権限で保存し、期限が近い（残り60秒以下）か 401 のときに署名し直す。取り消した端末のセッションは無効になる。

## 5. 接続とブロック（人と人）

接続は Person 単位。端末は関係しない。

| 操作 | 振る舞い |
|---|---|
| 要求（`POST /v2/connections`） | 相手の Person ID を指定する。相手からの要求がすでにあれば、それを承認したことになる。ブロックされていても、ブロックを知られないよう、ふつうの要求と同じ応答を返す |
| 承認（`…/:peer/accept`） | 届いた要求を承認する。承認しても共有は始まらない（共有には Client 側で別に許可が要る。[projects.md](projects.md)） |
| 拒否（`…/:peer/reject`） | 届いた要求を消す。相手には知らせない |
| 解除（`DELETE /v2/connections/:peer`） | 接続を消し、二人のあいだの未配送のメッセージも消す |
| ブロック（`PUT /v2/blocks/:peer`） | 接続を消し、未配送のメッセージを消し、ブロックを記録する。ブロックした相手からの承認待ちの要求は一覧に出さず、受け取る要求の枠にも数えない |
| ブロック解除 | ブロックを消し、その相手からの承認待ちの要求も消す |

上限: 1人が受け取る未処理の要求は100件、出せる承認待ちの要求は50件、ブロックは500件。承認も拒否もされない要求は14日で消える。

呼び名（連絡先の名前）は Relay には送らない。主人が接続の要求・承認のときに付け、Client の連絡先になる。接続が成立しても、呼び名がない相手は連絡先に入らない。その相手からの近況は、呼び名が付くまで手元に保留する（開かない）。

## 6. メッセージ

### 6.1 Narrative Message（暗号化される本文）

| 項目 | 内容 |
|---|---|
| `content` | 共有内容（「主人は〜」の三人称）。10〜200字 |
| `purpose` / `nuance` / `context` | 伝える目的・調子・話題の文脈（任意。各60字まで） |
| `useExpiresAt` | 受信側がこの情報を使ってよい期限（作成から最長7日） |
| `reshare` | `deny` / `allow`。受信側のエージェントが他の人へ伝え直してよいか |
| `periodStart` / `periodEnd` | 近況の時間帯（任意） |

送る前にも受け取った後にも、`normalizeNarrative` で正規化して確かめる。内容は友人のエージェントが書いた、信頼できない入力として扱い、正規化・長さ・命令に見える文の検出（`instruction_like`）・期限の妥当性を見る。検査の中身は [post-flow.md](post-flow.md)。

### 6.2 封筒（RelayEnvelope、v3）

Relay が運ぶのは暗号化した封筒だけ。

```
ヘッダ     v=3, suite, messageId, sender(Person), senderDevice, createdAt, deliveryExpiresAt
senderCert 送った端末の証明書
iv, ciphertext  本文（AES-256-GCM）
recipients[]    受信者の人ごと: { person, boxes[], sig }
  boxes[]       その人の端末ごと: { device, keyVersion, enc, wrapped }
```

- **本文**は、使い捨ての32バイトの鍵 K で AES-256-GCM で暗号化する。ヘッダ文字列を AAD にする
- **K は受信者の人の、取り消されていない端末ごとに HPKE（RFC 9180 の Base モード）で包む**。暗号スイートは DHKEM(X25519, HKDF-SHA256) / HKDF-SHA256 / ChaCha20-Poly1305 に固定し、封筒の `suite` に記録する。HPKE の info は `souieba/v2/cek`、AAD はヘッダ・受信者の Person ID・Device ID。包む相手の公開鍵が小さい位数の点なら断る
- **署名**は、受信者の人ごとに、送信した端末の署名鍵で行う。対象は、ヘッダ・iv・暗号文のハッシュ・受信者の Person ID・その人の端末ごとの箱（Device ID 順）。人ごとに別の署名にするのは、他の受信者が誰かを、Relay から各受信者へ渡さずに済ませるため
- メッセージ ID は `msg_` と16バイトの乱数の base64url（22文字）
- 宛先は1通あたり50人まで。1人の端末は10台まで

### 6.3 期限

| 期限 | 意味 | 既定 | 上限 |
|---|---|---|---|
| 配送期限（`deliveryExpiresAt`） | Relay が未配送のまま持つ期間 | 作成から3日 | 7日 |
| 利用期限（`useExpiresAt`） | 受信側が Tell に使ってよい期間 | 作成から2日 | 7日 |

送る側は、どちらも1時間〜7日に収める。作成時刻が Relay の受信時刻と10分以上ずれた封筒は、Relay も受信側も受け付けない。

## 7. 送信と配送

**送信**（`POST /v2/messages`）: Relay は、次を確かめる。

- 封筒の送信者が認証した端末と一致する。送った端末の証明書が、登録したものと完全に同じ
- メッセージ ID の形式と重複、作成時刻（±10分）、配送期限（未来で、作成から7日以内）、宛先の数・重複
- 宛先ごとの署名が、送信した端末の署名鍵で合う

そのうえで宛先の人ごとに、接続が承認済みで、相手にブロックされていなければ、その人の端末のうち、取り消されておらず**今の暗号化鍵の版で包まれた箱**だけを配送する。受け付けなかった人は理由（`not_connected`: 接続していない／ブロックされている、`stale_key`: 使える端末の箱がない）つきで返す。配送の対象は送信した時点の宛先と端末だけで、あとから接続した人や、あとから増えた端末には届かない。

Relay はメッセージ本文（暗号文）を共通部分として1つ、端末ごとの箱を配送レコードとして持つ。送信者が持てる未受信の配送は1万件まで。

**公開猶予**: 受信側に見えるのは、受け付けてから Relay の設定（`SOUIEBA_POST_GRACE_MINUTES`）の分だけ経ってから。送信者は、`DELETE /v2/messages/:id` で（同じ人のどの端末からでも）送ったメッセージを取り消せる。

**受信**（`GET /v2/messages`）: その端末宛てで、まだ受け取っておらず、猶予が終わっていて、配送期限内で、送信者が接続済みのものを、古い順に最大50件返す。各件には、その受信者の人の分の箱だけが入る。

**受け取りの記録**（`POST /v2/messages/ack`）: 端末分の箱を消し、受け取った時刻を記録する。宛先のすべての端末が受け取ったら、本文の暗号文も消す。配送の状態は、送信者が `GET /v2/messages/sent` で確かめられるよう、配送期限まで残す（人ごとに、どれかの端末が受け取っていれば delivered）。

**削除**: 配送期限を過ぎたメッセージ・期限切れのチャレンジとセッション・14日を過ぎた承認待ちの要求は、定期的に物理削除する（[server.md](server.md)）。

## 8. 受信側の検証

受信側（`RelayTransport`）は、Relay から受け取った封筒を次の順に検証し、1つでも落ちたら捨てる（理由は記録する）。

1. ヘッダの形（バージョン・スイート・ID・正規の ISO 日時）
2. 宛先が自分（Person と端末）で、自分の端末の箱がある
3. 送信者が連絡先にいる（いなければ、接続済みなら保留、そうでなければ破棄）
4. 送った端末の証明書が、**固定した送信者の Person 鍵**で署名されていて、取り消されていない
5. 箱の鍵の版が、自分の今の暗号化鍵の版と一致する
6. 受信者の人ごとの署名が、証明書の署名鍵で合う
7. 同じメッセージ ID をすでに受け取っていない（再配送の防止）
8. 配送期限内で、作成時刻が未来に10分以上ずれていない
9. HPKE で K を開き、本文を復号する
10. `normalizeNarrative` で中身を検査し、利用期限が切れていない

通ったものを手元の受信箱に入れ、Relay に ack を送る。Relay から来る文字列（エラーメッセージなど）も、エージェントが読む出力に入りうるので、形を確かめ、命令に見える文は使わない。

## 9. Relay に見える情報

| 見える | 見えない |
|---|---|
| Person ID・Person 公開鍵・端末証明書・取り消し | メッセージの本文（Narrative Message の全項目） |
| 誰と誰が接続しているか、承認待ちの要求、誰が誰をブロックしているか | 呼び名・グループ・共有先・Policy・プロジェクト |
| 誰のどの端末が、いつ、誰のどの端末に送ったか。受け取られた時刻 | メモ |
| 暗号文の大きさ、作成時刻・配送期限 | 利用期限・目的・ニュアンス・文脈（暗号化の中） |
| アクセスログの送信元 IP・経路・状態コード・所要時間 | 本文やトークン（ログに記録しない） |

## 10. 信頼モデルと限界

**Relay を信頼しなくてよい点**

- 本文は、受信者の端末の秘密鍵でしか開けない。DB・バックアップが漏れても、サーバの管理者が読もうとしても、本文は読めない
- 送信者を偽れない。送信者の端末証明書は送信者の Person 鍵で署名され、受信側が固定した Person 鍵で確かめる。Relay が偽の端末や鍵を配っても、署名が合わず使われない（送る側も同じ確認をしてから暗号化する）
- 以前確かめた取り消しと鍵の版は手元で覚えるので、Relay が取り消しを隠したり古い証明書を返したりしても、使わない

**信頼が要る点・限界**

- **最初の ID の交換**: Person ID を信頼できる経路で友人から受け取ることが前提。偽の ID に接続すれば、その相手に接続してしまう（Person ID は鍵の指紋でもあるが、誰のものかを教えるものではない）
- **Relay が止められること**: メッセージを配送しない・遅らせることはできる（本文は読めず、偽造もできない）。受信側が再配送を防ぐので、重複して伝わることはない
- **Relay が見るメタデータ**: 前節の表のとおり、誰が誰と接続し、誰がいつ誰に送ったかは Relay に見える
- **Forward Secrecy はない**。端末の暗号化鍵（長期）の秘密が漏れると、保存されていた過去の暗号文が読める。Relay は受け取られた暗号文を消す
- **鍵の更新・端末の取り消し・別の PC への引っ越し**: プロトコル（暗号化鍵の版を上げた証明書の再登録、取り消し）と Relay・受信側の検証は対応しているが、CLI にはそれを行う操作がない。Person の秘密鍵は最初の PC にだけあり、端末は `init` で作った1台だけを使う
- 友人の近況は信頼できない入力として扱う（Tell 文は LLM を通さずテンプレートで組む）。プロンプトインジェクションは根本的には防げず、正規化・命令に見える文の検出・表示名の検査で手間を増やして守る

## なぜこうしたか

- **ID を鍵から作る**: アカウントやログインコードを持たず、サーバに依存しない ID で人を指せるようにするため。Relay が公開鍵を配る立場でも、偽の鍵は Person ID と合わないので気づける。人ごとに1つにしたことで、友人から見える主体は1人になり、複数のエージェント（端末）は同じ人の端末として扱われる
- **端末証明書を Person 鍵で署名する**: エージェントごとに鍵を持たせつつ、友人には1人に見せるため。端末の名前は証明書に入れず、友人に見せない
- **人ごとに署名する**: 他の受信者が誰かを Relay から各受信者に渡さずに済ませるため
- **HPKE**: 独自の暗号を作らず、RFC 9180 の手順を `node:crypto` の部品だけで組んだ。CLI を外部依存なしで配るため、ライブラリは使わない。他の実装（`@hpke/core`）と相互に復号できることをテストで確かめている
- **受け取ったら鍵と暗号文を消す**: Relay に暗号文を長く残さないため
- **近況を LLM を通さずに見せる経路を作らない**: 近況は、エージェントが会話の中で「あ、そういえば」と伝える経路だけにした。体験を優先し、プロンプトインジェクションへは検出の強化で対応する
